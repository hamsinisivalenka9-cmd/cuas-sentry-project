=========================================================
WHY THIS STAGE EXISTS
=========================================================

Before explaining what this stage did, it helps to explain what the whole
project is trying to do. According to CLAUDE.md and AGENTS.md (two files in
the project root that both contain the same project instructions), the goal
is to build a Python program that reads a file full of sensor data
(data/input/sanitized.mcap) and loads it into a local database
(data/output/sentry.db) so that simple questions can be asked of it with
SQL, such as "what percentage of camera detections turned into tracked
objects?"

That end goal involves several risky, hard-to-reverse steps later on:
writing a database schema, writing code that reads and deletes/rebuilds
that database, and writing code that parses a specialized binary file
format. None of that should be attempted on a machine that might not even
have the right tools installed, or against a source file that might not
exist, might be corrupted, or might not be safely readable.

Stage 1 exists to answer one question with certainty before any other work
begins: "Can we even do this, on this machine, right now?" Specifically it
checks:

- Does the source data file actually exist at the path the project expects?
- Is that file protected from being accidentally committed to git (since
  CLAUDE.md rule #2 says the source file and the generated database must
  never be committed)?
- Is there a working Python installation, and a project-specific virtual
  environment (a private, isolated copy of Python and its packages, so this
  project's dependencies do not interfere with anything else on the
  machine)?
- Are the specific third-party libraries this project depends on
  (mcap, mcap-protobuf-support, protobuf, pytest) actually installed in
  that environment?
- Does Python's built-in database module (sqlite3) work at all on this
  machine?
- Can the source file be opened in a safe, read-only way without writing to
  it?

This could not safely be skipped because CLAUDE.md rule #1 is "Never
modify, delete, rename, move, or overwrite the source MCAP file." The
source file is the only copy of the raw sensor data available to this
project. If later stages had assumed the file existed, or assumed a package
was installed, or assumed sqlite3 worked, and any of those assumptions had
been wrong, the failure could have happened in the middle of a file-writing
operation -- which is exactly the situation where a source file is most at
risk of being damaged. Verifying everything read-only, up front, in a
dedicated stage, means every later stage can build on a known-good
foundation instead of discovering a missing dependency halfway through a
database rebuild.

If this stage had been skipped, the risks would have included: writing an
inspection or ETL script against a file path that does not exist (wasted
work, confusing errors), silently committing a multi-megabyte sensor data
file or a generated database file to git (against explicit project rules,
and a real risk to repository size and possibly to data sensitivity), or
discovering only much later that a required package was missing or
mismatched, after already writing code that depends on it.

Decision: Verify everything read-only, before writing any inspection or
pipeline code.
Reason: The source file is irreplaceable within this project (rule #1), and
several early assumptions (file exists, packages installed, sqlite3 works)
could each independently block or corrupt later work if wrong.
Alternative considered: Skip straight to writing the MCAP inspection script
and let it fail naturally if something was missing.
Why the chosen approach is better: A failure inside a larger script is
harder to diagnose (was it the file? the package? the database engine?).
A dedicated verification stage isolates each check, so any failure has an
obvious, specific cause. It also means no time is wasted writing inspection
logic against a file or environment that was not actually ready.
Future impact: Every later stage can simply assume the environment works,
instead of re-checking it, which keeps later scripts focused on their own
job (inspecting data, analyzing keys) instead of repeating setup checks.

Decision: Confirm the .gitignore exclusion using git's own
`git check-ignore` command, not just by reading the text of .gitignore.
Reason: A .gitignore rule can look correct on paper but not actually match
the intended file (for example, due to a typo in the path, or a rule that
only matches in certain directories). Asking git directly is the only way
to be certain.
Alternative considered: Trust the .gitignore file's text alone.
Why the chosen approach is better: it tests the real behavior of the tool
that matters (git), not just the configuration intended to produce that
behavior.
Future impact: gives real confidence, backed by tool output, that the
source file and (later) the generated database will not be accidentally
committed.

Decision: Record an MD5 checksum of the source file as an extra,
unrequested safety measure.
Reason: The six checks explicitly asked for did not include a way to prove,
after the fact, that the file was never modified. A checksum makes that
provable rather than assumed.
Alternative considered: Rely on "we only opened it in read-only mode" as

Why the chosen approach is better: read-only mode prevents accidental
writes through that particular file handle, but a checksum is independent,
external proof that covers the whole file and can be re-checked at any
later point, by anyone, regardless of what code path touched the file.
Future impact: this checksum was in fact re-verified after Stage 2 and
Stage 3, giving concrete evidence (not just a promise) that the source file

=========================================================
BEGINNER TAKEAWAYS
=========================================================

- A "virtual environment" (seen as the `.venv/` folder) is a private,
  isolated copy of Python and its installed packages, kept separate from
  whatever Python is installed on the rest of the computer. This means the
  specific package versions this project needs cannot be accidentally
  broken by, or conflict with, some other unrelated project on the same
  machine.

- "protobuf" (short for Protocol Buffers) is a format created by Google for
  packing structured data (numbers, text, nested groups of fields) into a
  small, efficient binary format, along with a schema (a definition of what
  fields exist and what type each one is) that describes how to unpack it
  again. The sensor data in this project's source file is stored using
  protobuf.

- "MCAP" is a file format (pronounced like "em-cap") designed for
  recording streams of timestamped messages from robots, sensors, and
  similar systems -- think of it like a black-box flight recorder file
  format. It can store many different kinds of messages (in this project,
  four different kinds, one per "topic") in a single file, each message
  timestamped and tagged with which topic it belongs to. The MCAP file
  itself doesn't know or care that the messages inside it happen to be
  protobuf -- that's a separate, additional detail this project also has to
  handle.

- A file's "magic number" is a short, fixed sequence of bytes that a file
  format specification requires every valid file of that type to begin
  with. Checking it is a fast, reliable way to confirm a file really is
  what its name/extension claims, before trying to do anything more
  complicated with it.

- An "MD5 checksum" is a short fingerprint (a string of letters and
  numbers) calculated from a file's exact contents. Any change to the file
  -- even a single byte -- produces a completely different checksum. This
  makes it a simple, reliable way to prove a file has (or has not) been
  modified between two points in time.

- SQLite is a database engine that stores an entire database as a single
  file on disk, with no separate server process required. It is well
  suited to a local, self-contained project like this one. "Foreign-key
  enforcement" is a database feature (not on by default in SQLite, which is
  why CLAUDE.md rule #8 calls it out specifically) that makes the database
  reject data that would break a declared relationship between two tables
  -- for example, refusing to insert a "detection" row that claims to
  belong to a "track" that doesn't exist. This project has not designed
  those tables yet, but confirming this feature works was a necessary early
  step.

STAGE 8 SUMMARY — Streamlit Analytical Dashboard
=======================================================================

SCOPE
-----
Built a read-only Streamlit dashboard over the completed ETL pipeline,
SQLite database, and 22-query analytical SQL library. No change to
sql/schema.sql, sql/indexes.sql, sql/views.sql, sql/validation.sql, any
src/cuas_etl/*.py module, or any file under queries/. The dashboard is
strictly a presentation layer: every number, chart, and table comes
from executing an existing .sql file read-only; nothing is recomputed
or reimplemented in Python.

DEVIATIONS FROM THE PROPOSED FILE LIST
------------------------------------------
Two small additions beyond the approved plan, both flagged here for
visibility (also documented in docs/dashboard/DASHBOARD_GUIDE.md):
  1. dashboard/__init__.py and dashboard/components/__init__.py --
     required for `dashboard.*` to resolve as a proper Python package.
  2. dashboard/components/sidebar.py -- Streamlit's multipage model
     runs each pages/*.py file as an independent script; the shared
     sidebar (project overview, DB status, navigation) needed a home
     every page could import without re-triggering app.py's own
     st.set_page_config(). Contains only structural DB metadata
     display, no analytical logic.

PAGES CREATED
-------------
1. Executive Dashboard -- KPI row (9 metrics), CV detection-to-track
   funnel, sensor utilization, Drone/Airplane duration comparison (the
   protected checksum result, arithmetic mean primary + documented
   caveat), multi-sensor vs. single-sensor comparison, duration by
   exact sensor combination, data-quality issue summary, Key Findings.
2. Operations Dashboard -- CV/fused track selectors (the only 2 real
   parameterized filters in the query library), longest-lived tracks,
   CV track history, fused track history, sensor contributions per
   fused track, classification changes over time, CV focus quality vs.
   incorporation, CV detection quality vs. track persistence,
   classification stability vs. measurement support. Explicit callout
   that CV and fused tracks are never joined by ID.
3. Technical Dashboard -- database metadata, live integrity/FK checks,
   optional "Run validation" button (subprocess to the unchanged
   scripts/run_validation.py), all 6 technical queries with status
   banners.
4. Query Explorer -- browse/filter/run/download any of the 22 approved
   queries; only executes files already on disk, never accepts
   arbitrary SQL or a filesystem path.

QUERIES REUSED
--------------
All 22 existing queries (21 from Stage 7/7B + the preserved legacy
queries/fused_track_duration_by_type.sql) are wired into the dashboard.
Zero new .sql files were created. Per explicit approval, 3 KPIs reuse
already-computed rows from existing queries rather than requiring new
single-purpose SQL:
  - "Total Fused Tracks" and "Total Radar Detections" (Executive page)
    select the matching row out of
    queries/technical/table_row_count_reconciliation.sql's existing
    output.
  - "Data-Quality Issues" total (Executive page) sums the issue_count
    column already returned by
    queries/executive/data_quality_issue_summary.sql.
This is presentational aggregation of an already-fully-computed SQL
result (picking/summing rows a query already produced), not a
re-derivation of business logic in Python.

NEW QUERIES ADDED
------------------
None. Per instruction, no new SQL was created solely to support
dashboard KPIs.

LIMITATIONS
-----------
- Only 2 real parameterized filters exist (:track_id, :fused_track_id)
  -- no result-limit, min-duration, object-class, focus-quality, or
  sensor-type filter is offered, since none is backed by a
  parameterized query (per explicit instruction not to add filters
  that can't be applied safely through parameterized SQL).
- The Query Explorer and Operations page selectors are populated by 2
  tiny, non-analytical identity-list lookups defined directly in
  sql_loader.py (not a queries/*.sql file) -- documented and tested as
  a narrow, approved exception.
- Streamlit AppTest exercises each page's server-side logic and
  confirms no exception is raised, but does not replace a human
  visually reviewing the running app in a browser (see screenshot
  instructions below).
- The development machine's disk was critically low on space
  (encountered "No space left on device" mid-install) -- resolved by
  purging the pip cache (a safe, standard, fully reversible cleanup),
  but disk usage remains a systemic, machine-level concern outside
  this project's scope; flagging for awareness, not attempting further
  cleanup without explicit direction.

CONFIRMATIONS
-------------
- No ETL file changed: src/cuas_etl/{extract,transform,load,validation,database}.py
  are byte-for-byte unchanged from before this stage.
- No schema file changed: sql/{schema,indexes,views,validation}.sql are
  byte-for-byte unchanged.
- SQLite remained read-only throughout: every dashboard connection uses
  mode=ro + PRAGMA query_only=ON; a direct write attempt through it

  content diff before/after running all 22 queries shows zero change.

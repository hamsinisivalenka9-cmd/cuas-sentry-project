=========================================================
WHY THIS STAGE EXISTS
=========================================================

Stages 1-3 spent real effort making sure nothing about this project's
database would be designed from guesswork: Stage 1 confirmed the tools
worked, Stage 2 mapped out what the source file actually contains, and
Stage 3 proved, field by field, which identifiers are trustworthy and
which same-named fields across topics are actually related. All of that
work exists to feed into exactly one moment: the point where actual
tables, keys, and relationships get decided. This stage is that moment.

This could not safely be skipped, and could not safely be rushed, because
a database schema is one of the most expensive things to redesign after
the fact -- once an ETL pipeline is loading real rows into real tables
with real foreign-key constraints, changing the grain of a table or
swapping a primary key touches every piece of code and every query built
on top of it. CLAUDE.md's rules exist specifically to prevent this kind of
costly rework: rule 6 requires every table's grain to be explicit up
front, rule 7 requires keys to be justified by evidence rather than
convention, and rule 14 forbids hard-coding the analytical answers the
schema is supposed to help compute honestly. Skipping straight to writing
schema.sql, without this documentation step, would have risked repeating
the exact kind of unjustified, name-based assumption Stage 3 was built to
catch -- just one level further downstream, in a place (a live database
schema) that is much harder to walk back.

=========================================================
WHAT WE ACCOMPLISHED
=========================================================

This stage happened in three rounds, each one narrowing and correcting the
last -- itself a good illustration of why design review before
implementation matters.

1. First proposal: a ~28-32 table, fully-normalized design.
   What was done: every genuinely repeated nested protobuf structure
   across all four topics was mapped to its own table -- per-topic frame
   tables, a child table for every repeated field under track_states
   (which alone has over a dozen), enum lookup tables, and so on.
   Why: this is what "textbook" normalization looks like when applied
   mechanically to a schema this deeply nested.
   What was learned: the user's review correctly identified this as too
   complex for the assessment's actual goal -- readable, maintainable,
   analytically useful, not maximally normalized. This was a real, useful
   course correction, not a rejection of the underlying analysis; every
   fact discovered in the first pass was still valid, just organized at
   the wrong altitude.

2. Second proposal: a compact, ~10-table redesign.
   What was done: the architecture was rebuilt around a much stricter
   test -- only create a separate table for something that is a distinct
   entity, a time-series history, a genuine many-to-many relationship, or
   repeated data actually needed by one of the six required analytical
   queries. Structures that were confirmed always-empty, or that would add
   a join without analytical value, were flattened, stored as compact
   JSON, or omitted outright, each with a documented reason.
   Why: to directly satisfy the explicit requirement that another engineer
   should be able to understand the schema quickly.
   What was learned: a 10-table design, closely following a compact model
   the user sketched directly, could still support every one of the six
   required analytical questions with at most two table joins each -- the
   complexity reduction did not cost analytical power.

3. Third round: four specific issues investigated with real evidence
   before the design was finalized (each covered in detail in its own
   section below): the CV-incorporation percentage discrepancy, two
   candidate self-referencing relationships that Stage 3 could not
   confirm, whether to store derived track-duration timestamps, and how to
   handle one remaining repeated nested field (measurement-to-detection
   links).
   What was done: rather than resolve these by design-time judgment alone,
   several new, full-dataset, read-only queries were run directly against
   the real source file (never modified -- see Validation below) to settle
   each question with evidence.
   What was learned: this produced the single most important finding of
   the whole stage -- see "What We Discovered" below.

4. Wrote the four full design documents plus this summary, then ran a
   consistency pass across all of them to make sure table names, primary
   keys, foreign keys, grains, and row-count estimates match exactly
   everywhere they are repeated.

WHAT WE DISCOVERED
=========================================================

- The CV detection-incorporation percentage in this file is genuinely
  higher than the project's ~81% approximate target -- not lower, and not
  close. Every field that could plausibly serve as the association source
  was enumerated directly from the real protobuf schema (not assumed):
  the only one that exists is `last_associated_detection_id`. Counting
  distinct detections referenced by it gives 1,868 of 1,911, or 97.75%. A
  second, independent field on the same message -- a cumulative counter
  called `num_detection_associations`, not previously analyzed in Stage
  2/3 -- was checked as a cross-validation and points to an even higher
  figure, effectively 99.9%. No filter on either the detection side
  (disposition, suppression flags) or the track side (status) that could
  be justified by real data brought the number down toward 81%.
  Why it matters: this is now a clearly documented, evidence-backed,
  unresolved discrepancy -- not a bug in this project's analysis, and not
  something papered over with an invented filter to make the numbers
  match. Whoever answers this question next has concrete numbers and a
  concrete methodology to start from, and an explicit warning not to
  assume the ~81% target was simply "the right answer this data should
  produce."

- The fused-track classification system cannot represent "Drone" or
  "Airplane" at all, as a matter of schema design, not just missing data.
  Every value of the `proto.tower.TrackObjectClass` enum (the type used by
  the "fused" track_states topic, the one CLAUDE.md's duration question is
  really about) was read directly from the protobuf descriptor: none of
  them is named anything like DRONE or AIRPLANE. Separately, even the
  richer CV classification enum, which does define explicit DRONE and
  AIRPLANE values, was checked against what this file actually contains --
  and neither value is ever used; every CV track in this file is
  classified only as the more generic AIR_VEHICLE or BIRD.
  Why it matters: this means the second of CLAUDE.md's two target
  analytical questions cannot currently be answered honestly from this
  file at all, for two independent reasons, not one. This needed to be
  discovered and documented now, before an ETL stage tried to compute an
  average duration for a classification that either doesn't exist in the
  schema or was never used in the data.

- A systemic pattern first seen in Stage 2 -- fields that are structurally
  present but always empty -- continued to hold up under the much more
  targeted checks run in this stage: CV detection disposition, radar
  object classification, and fused track_quality were all confirmed, via
  full-dataset queries, to be constant/empty across every single row.
  Why it matters: this ruled out several tempting-looking filters that
  might otherwise have been used (incorrectly) to try to explain the 81%
  discrepancy, and confirms the schema's decision to keep these as
  nullable columns rather than build any logic around them.

- Two genuinely repeated structures survived close evaluation and still
  did not become separate tables: `track_states.sensors` turned out to be
  a near-duplicate of the `measurements` structure already modeled
  (both describe sensor involvement in a fused-track update), and the
  radar `cluster` self-referencing structure was confirmed to be always
  empty, with no identifier field on the underlying message that a
  self-referencing key could even point to.
  Why it matters: this is direct, checked evidence that the compact design
  is not simply "the simpler option was chosen without looking" -- each
  omission was specifically investigated and is defensible.

=========================================================
ENGINEERING DECISIONS
=========================================================

Decision: Investigate the 81% discrepancy with real, full-dataset queries
before finalizing any table, rather than accept the first plausible number
computed.
Reason: the user's explicit instruction was not to finalize the bridge
table or claim the question solved until the discrepancy was understood --
and, separately, this is simply good practice: a percentage this far off
from the expected target (97.8%-99.9% vs. ~81%) is a signal worth chasing
down, not rounding away.
Alternative considered: report the 97.8% figure as "the" answer and move
on, noting the target was "approximate" anyway.
Why the chosen approach is better: the investigation surfaced a second,
independent field (`num_detection_associations`) that had not been
examined in Stage 2/3 at all, and definitively ruled out several plausible
explanations (denominator filtering, numerator filtering) rather than
leaving them as untested guesses. This turns "the number doesn't match"
into a specific, well-evidenced, actionable open question instead of a
shrug.
Future impact: whoever picks up the ETL stage does not need to re-derive
this investigation from scratch -- the methodology, the fields checked,
and the reasons each alternative was ruled out are all documented in
docs/architecture/DATABASE_DESIGN.md Section 2.

Decision: Do not enforce parent_object_track_id, the radar cluster
structure, or radar_detections.track_id as foreign keys.
Reason: direct instruction, backed by Stage 3 evidence -- each of these
was already classified as either unconfirmed ("weak heuristic"), entirely
unpopulated, or actively rejected (zero value overlap even where types
matched).
Alternative considered: enforce them anyway, since the columns exist and
"look like" foreign keys by name.
Why the chosen approach is better: CLAUDE.md rule 8 requires foreign-key
enforcement to actually be turned on; enforcing a relationship the real
data does not support would either make otherwise-valid rows fail to load,
or require silently coercing/faking data to satisfy a constraint that was
never actually justified -- the opposite of rule 7's "keys only when
justified."
Future impact: the schema is safe to load real data into with foreign
keys fully enabled, without any of these three columns causing a load
failure or requiring a workaround.

Decision: Do not store first-observed time, last-observed time, or
duration as columns on the persistent-entity tables (cv_tracks,
fused_tracks); describe MIN/MAX-based views instead.
Reason: direct instruction, for a sound reason -- these tables' underlying
state-history tables are append-only and keep growing, so a stored
duration would need constant re-computation to stay correct, and any gap
in that re-computation creates a duplicated fact that has silently gone
stale.
Alternative considered: store these as columns anyway, refreshed by a
scheduled job or trigger.
Why the chosen approach is better: a view recomputes from the current
state rows every single time it is queried, so the derived fact can never
disagree with its source, by construction -- no refresh job to forget to
run, no trigger to get out of sync.
Future impact: the eventual ETL/implementation stage has two named,
described views (v_cv_track_summary, v_fused_track_summary) ready to
create, with the SQL shown as illustrative documentation, not yet
implemented.

Decision: Store the repeated measurement-to-detection links as compact
JSON on the fused_track_measurements table, not as an eleventh bridge
table.
Reason: none of the six required analytical queries need a relational
join on these specific ids; adding a table for a two-levels-deep link with
no current requirement would directly contradict the "no joins without
analytical value" instruction for this stage.
Alternative considered: build fused_measurement_detection_links as a full
bridge table, matching the pattern used for cv_detection_track_links.
Why the chosen approach is better: cv_detection_track_links exists because
Stage 3 explicitly proved that exact relationship was needed for a
required analytical question; this one has not been shown to be needed
yet, and the JSON approach preserves full fidelity so nothing is lost by
waiting.
Future impact: documented upgrade path -- if a future stage needs to
analyze which specific CV detections fed into fused-track measurements,
the JSON can be promoted into a real table with no data loss, since the
JSON already holds everything a bridge table would.

INTERVIEW EXPLANATION
=========================================================

"By the time I got to actually designing the database, I'd already done
two rounds of investigation into the real data, so my first instinct was
to be thorough -- I mapped essentially every repeated structure in the
protobuf schema to its own table, which got me to around thirty tables.
That was technically defensible, but when I got feedback that it was too
complex for what this was supposed to be -- a clean, readable design
another engineer could understand quickly -- I didn't just trim a few
tables, I changed the test I was applying. Instead of asking 'does this
repeated structure exist,' I started asking 'does this represent a real
entity, a real history, a real many-to-many relationship, or data
actually needed for one of the required queries.' That got me down to ten
tables without losing any analytical power -- every required query still
only needs one or two joins. But the part I think mattered most happened
after that: before I'd let myself finalize the one table everyone would
actually care about -- the bridge table linking detections to tracks -- I
went back to the real data one more time, because the number it produced,
about 98%, didn't match the project's own expected answer of about 81%.
I could have just noted the difference and moved on, but instead I
actually enumerated every field on the track message directly from the
protobuf schema to make sure I wasn't missing another way detections get
linked to tracks, and I found a second field, a cumulative counter, that
nobody had looked at yet. It agreed with my first number, not with the
target -- which told me the discrepancy was real, not a bug in my
analysis, and I documented it as an open question instead of quietly
forcing my design to produce 81%. I did the same thing for the second
analytical question in the brief, about drone versus airplane duration --
and found that the fused-tracking system's own classification scheme
literally doesn't have a category for drone or airplane, it only has
broader categories like 'air vehicle.' That's the kind of finding you can
only get by actually going back to the source data with a specific
question, instead of trusting that the schema will obviously support
whatever the assignment brief assumed it would."

=========================================================
BEGINNER TAKEAWAYS
=========================================================

- "Normalization" is not an all-or-nothing property -- it's a spectrum,
  and more normalized is not automatically better. A textbook-perfect,
  fully-normalized design can be genuinely worse for a specific project if
  it becomes too complex for the people who have to build and query it to
  understand quickly. Good database design means picking the right amount
  of normalization for the actual job, not the maximum possible amount.

- A "grain" (what one row represents) and a "surrogate key" (a made-up id
  column, usually just a counting number, added purely to guarantee
  uniqueness) are two of the most important, and most permanent,
  decisions in any database design. This project consistently preferred a
  surrogate key over a natural one whenever there was any real doubt about
  whether the natural option would stay unique forever -- because
  discovering later that a "unique" natural key wasn't actually unique
  can break a database in a way that's very hard to fix after real data
  has been loaded.

- A "view" is a saved SQL query that looks like a table when you query it,
  but doesn't actually store any data of its own -- every time you ask it
  a question, it recalculates the answer from the real tables underneath.
  This project chose to compute things like "how long has this track been
  observed" using a view instead of storing that number directly, because
  a stored number has to be actively kept up to date every time new data
  arrives, while a view is automatically always correct, because it's
  recalculated fresh every time.

- Just because a question sounds simple in a project brief -- "what
  percentage of detections became tracks" -- does not mean the raw data
  contains one, unambiguous way to compute it. This stage found at least
  two structurally different but both-defensible ways to compute that
  exact percentage, producing different numbers, neither of which matched
  the brief's own expected answer. Recognizing that kind of ambiguity, and
  documenting it honestly instead of picking whichever number looks
  right, is a core, real skill in data engineering -- not a failure to
  find "the" answer.

- An "enum" (short for enumeration) is a fixed, predefined list of
  allowed values for a field -- like a multiple-choice question instead
  of free text. This project discovered that two different parts of the
  same data used two different enums for "what kind of object is this,"
  and one of those enums simply didn't include the specific options
  ("drone," "airplane") the project needed -- a good example of how a
  seemingly small schema detail, several layers deep in someone else's
  data format, can completely block a question you want to ask of it.

EXECUTIVE SUMMARY
=========================================================

Building on three prior stages of environment verification, structural
inspection, and identifier analysis, this stage designed the project's
complete relational database schema: 10 tables, each with an explicit
grain, evidence-justified primary and foreign keys, and a clear reason for
existing (or, for several considered-and-rejected alternatives, a clear
reason for not existing). The design went through two full revisions
based on review -- first cut from roughly 30 tables to 10 for readability
and analytical simplicity, then refined again to remove two
unenforceable foreign-key relationships, replace stored (and
inevitably-staleness-prone) duration columns with recomputing views, and
settle a JSON-versus-bridge-table trade-off with a documented, reversible
decision. Along the way, this stage's most substantive work was a real
data investigation, not a design exercise: verifying, against the full
57,266-message source file and via direct protobuf reflection (not
memory), that the project's expected "~81% of detections incorporated
into tracks" validation target is not reproduced by any evidence-supported
method (the real figure is 97.8%-99.9%), and that the project's second
target question, comparing drone and airplane track durations, currently
cannot be answered at all -- not because of missing data, but because the
relevant classification system's enum has no such categories, and even
the richer system that does never actually uses them in this file. Both
findings are documented prominently and left unresolved, exactly as
instructed, rather than papered over to make the numbers match
expectations. No schema.sql, database, or ETL code was written -- this
stage produced documentation only, ready to be implemented, reviewed, and
tested in the next stage.

=========================================================
STAGE 5A SCHEMA REVIEW (ADDENDUM, 2026-08-06)
=========================================================

Before any schema.sql or database was implemented, this Stage 4 design
was put through a skeptical senior-data-engineering review, documented in
full in docs/architecture/SCHEMA_REVIEW.md and summarized on its own terms in
docs/stages/STAGE_05A_SUMMARY.txt. This addendum records, briefly, what that
review changed about this stage's design -- the full reasoning lives in
those two documents, not repeated here.

Issues found:
Nine findings, each tagged as a confirmed defect, a design improvement, a
documentation ambiguity, a performance optimization, or an unresolved
question (never blended together). The two most substantial: first, the
ETL loading order implied by this stage's design was incomplete -- it
never stated that cv_tracks and fused_tracks (both derived from distinct
values in their own child tables' source data) must be fully populated by
an upfront scan before any dependent row is inserted, which a naive
single-pass streaming loader would violate under PRAGMA foreign_keys = ON.
Second, two fields relevant to the still-unresolved classification
questions -- cv_tracks.tracks[].class_distribution and
track_states.object_class_confidence -- had never actually been measured
before this design chose to omit or ignore them; the review measured both
directly against the full file for the first time.

Corrections made:
An explicit two-phase loading strategy was documented (envelope and
identity tables first, in a complete pass; everything else second) --
not a relaxation of foreign-key enforcement, per explicit instruction.
Two redundant secondary indexes (each already covered by an existing
UNIQUE constraint's automatic index) were removed. Two new columns were
added: cv_track_states.object_class_confidence and
fused_track_states.object_class_confidence, both confirmed fully
populated once actually checked. Two radar columns were renamed,
azimuth->azimuth_rad and elevation->elevation_rad, after their units were
empirically confirmed (not previously stated or verified) from observed
value ranges matching [0, 2*pi]. Several radar columns (range,
range_rate, snr, filter_type, estimated_width_meters, is_marked) were
confirmed always-empty/constant across the full file and annotated as
such. One implicit design choice (that cv_track_states.last_associated_
detection_id is deliberately not foreign-key-enforced, unlike the
derived bridge table) was made explicit rather than left for a future
implementer to infer or get wrong.

Design decisions retained:
All 10 tables, and all 14 named key/constraint decisions the review was
asked to re-check, were retained without reversal -- the natural-key
choices for cv_detections/cv_tracks/fused_tracks, the surrogate-key
choices for source_messages/cv_track_states/fused_track_states, the
non-enforcement of the three rejected cross-topic relationships, the
JSON-not-bridge-table choices for detection_ids_json and cluster_json,
and the views-not-stored-columns choice for track duration, all held up
under skeptical review. This was a real finding in itself: a healthy
review does not need to invent structural changes to justify having
happened.

Remaining risks:
The two headline unresolved questions from Stage 4 -- the ~81% CV-
incorporation target not being reproduced by any evidence-based method,
and the Drone/Airplane duration question being unanswerable given the
fused classification enum's actual values -- were re-examined with new
evidence in this review and were NOT resolved; if anything, the new
class_distribution evidence reinforces both conclusions rather than
weakening them. A new, related open question was also surfaced: 18 of
103 persistent fused tracks genuinely change classification within their
own history, meaning "the" class of a fused track is itself an
unresolved modeling decision (five candidate resolution rules were
compared, and none was chosen, per explicit instruction) -- independent
of, and in addition to, the Drone/Airplane blocker. Finally, radar
analysis in this file was found to have a narrower real evidentiary base
than the original column list implied: once every confirmed-empty field
is set aside, only azimuth, elevation, track_id, and capture_time carry
real signal.

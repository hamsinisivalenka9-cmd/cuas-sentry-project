STAGE 7 SUMMARY — Analytical SQL Layer
=======================================================================

SCOPE
-----
Built a reusable, read-only analytical SQL layer on top of the
completed Stage 6/6B database. No change to sql/schema.sql,
src/cuas_etl/extract.py, transform.py, load.py, or validation.py.
Stage 6 remained strictly read-only throughout, as required.

Initial plan proposed 27 candidate queries; per approval, trimmed to
18 well-designed queries prioritizing quality over quantity, plus the
pre-existing queries/fused_track_duration_by_type.sql left exactly
where it is (per explicit instruction not to move/rename an artifact
existing tests and docs already reference).

Mid-implementation, the design philosophy was revised to prioritize
cross-table, relationship-driven analytical queries over isolated
single-table summaries, demonstrating why the data was normalized into
related entities rather than one flat table. The query set below
reflects that revision: 5 executive queries were replaced/added
(cv_detection_to_track_funnel.sql, multi_sensor_tracks_duration_
comparison.sql), 2 operational queries were deepened with new joins
(cv_track_history.sql now joins cv_track_class_distribution;
fused_track_history.sql now joins fused_track_measurements), 2
operational queries were merged (longest_lived_cv_tracks.sql +
longest_lived_fused_tracks.sql -> longest_lived_tracks.sql) and one
added (object_class_changes_over_time.sql), and one technical query
was replaced with a stronger relational-integrity check
(publish_vs_log_time_latency.sql -> source_message_child_
reconciliation.sql, with its finding folded into recording_
overview.sql instead).

IMPORTANT DESIGN CONSTRAINT HONORED: this project's own Stage 3
investigation (docs/data/KEY_ANALYSIS.md) confirmed CV-track identity and
fused-track identity are unrelated namespaces (zero value overlap,
incompatible types uint64 vs. TEXT). No query in this stage joins the
CV side to the fused side on any track-id-shaped column, even where a
generic "detection -> track -> fusion" pipeline diagram might suggest
one. Where both systems needed to appear together
(longest_lived_tracks.sql), an explicit UNION ALL with a track_type
label is used instead of a fabricated join. This is documented
prominently in docs/analytics/ANALYTICAL_INSIGHTS.md.

KEY ANALYTICAL FINDINGS (see docs/analytics/ANALYTICAL_INSIGHTS.md for full detail)
---------------------------------------------------------------------------
1. CV incorporation: 97.54% (1,864/1,911) -- confirmed stable, matches
   the protected Stage 6B figure exactly. Does not match the
   assignment's ~81% target; Anduril reviewed and confirmed no further
   investigation needed (docs/analytics/CHECKSUM_RESOLUTION.md).
2. Drone/Airplane: Drone n=51 mean 35.86s (target ~30s, +19.5%,
   honestly reported); Airplane n=36 mean 614.68s (target ~600s,
   +2.4%). Unchanged from Stage 6B.
3. Multi-sensor fused tracks are SHORTER-lived on average than
   single-sensor tracks (69.92s vs. 255.75s) -- a genuinely
   counter-intuitive finding, explained by sensor-type confounding
   (the multi-sensor group is exactly the short-range camera-visible
   tracks).
4. CV focus quality strongly correlates with incorporation rate
   (99.89% SHARP down to 22.22% BLURRY) -- already tested and rejected
   as an explanation for the CV-incorporation checksum gap, but a
   genuine standalone sensor-engineering finding.
5. Exactly 18 of 103 fused tracks change classification during their
   own lifetime -- an exact match to docs/architecture/SCHEMA_REVIEW.md finding F6,
   now directly queryable via object_class_changes_over_time.sql.
6. Zero publish/log-time latency across all 57,266 messages in this
   recording.
7. All 6 technical/data-quality queries return a clean (zero-violation)
   result: row counts match documented grain, zero duplicate bridge
   pairs, zero incomplete/misordered class-distribution groups, zero
   enum-resolution inconsistencies across 16 checked column pairs, and
   zero orphaned source_message_id references across 4 checked tables.

LIMITATIONS
-----------
- CV and fused track identities are never joined to each other, per
  the Stage 3 evidence discussed above -- any future query needing to
  correlate the two systems would need new source-supported evidence
  first, not an assumed join.
- Radar-side analytical value is limited in this specific recording,
  since most radar_detections fields are CONFIRMED constant/empty
  (docs/architecture/DATABASE_DESIGN.md Section 5.6) -- flagged as future work in
  docs/analytics/ANALYTICAL_INSIGHTS.md rather than forced into a query with
  little to show.
- object_class_changes_over_time.sql reports the raw classification
  sequence; it does not resolve "the" correct class per track (5
  documented resolution semantics exist, none selected).
- run_analytics.py's parameter-detection regex is a simple heuristic
  (documented in its own docstring), not a full SQL parser.

SCOPE
-----
Reviewed the completed Stage 7 library (queries/executive/,

radar_detections to any track identity is possible without asserting a
relationship the evidence rejects.

GAPS IDENTIFIED
----------------
1. No query connected CV detection input quality to CV TRACK-level
   persistence (only to binary incorporation).
2. No query broke fused-track duration down by the exact sensor
   combination (only binary multi-/single-sensor).
3. Classification stability (the 18-of-103 unstable tracks) was
   reported in isolation, never correlated against an explanatory
   factor.
4. radar_detections remains analytically isolated -- confirmed
   non-fillable, not attempted.

QUERIES ADDED (3, all new joins, none redundant with Stage 7)
-------------------------------------------------------------------
queries/operational/cv_detection_quality_vs_track_persistence.sql
  cv_detection_track_links -> cv_detections -> v_cv_track_summary.
  Finding: the 2 shortest CV tracks also have the 2 lowest average
  detection scores and 0% sharp-focus detections; relationship visible
  at the extremes, not strictly monotonic across all 17 tracks.

queries/executive/fused_track_duration_by_sensor_combination.sql
  fused_track_measurements -> fused_track_states -> v_fused_track_summary,
  grouped by the exact sorted set of contributing sensors (not just a
  count). Finding: exactly 3 combinations exist in this file
  (TRANSPONDER alone, CAMERA+RADAR, RADAR alone) -- no
  camera+transponder or radar+transponder pairing ever occurs. This
  resolves Stage 7's "multi-sensor tracks are shorter-lived" finding:
  it is not a general multi-sensor effect, it is that the only
  multi-sensor population (camera+radar) happens to be short-range
  engagements that never overlap with the long-duration
  transponder-only population.

queries/operational/fused_track_classification_stability_vs_measurement_support.sql
  fused_track_states (self-compared via LAG for stability) joined to
  fused_track_measurements (per-track measurement/sensor counts) joined
  to v_fused_track_summary (duration). Finding: the 18
  classification-unstable tracks are NOT under-measured relative to
  their own (much shorter) lifetimes -- they average slightly MORE
  distinct sensor types (1.22 vs. 1.06) than the 85 stable tracks. The
  naive "instability = poor sensor support" hypothesis is not
  supported.

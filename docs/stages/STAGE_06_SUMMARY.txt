DATA-QUALITY FINDINGS (never hardcoded — computed at build time)
------------------------------------------------------------------
1. CV detection-incorporation rate, computed directly from the loaded
   database: 1,864 of 1,911 cv_detections rows appear in
   cv_detection_track_links = 97.54%.
   This does NOT match CLAUDE.md's stated approximate validation target
   of ~81%. This discrepancy was investigated and documented in Stage 4/5
   (docs/architecture/DATABASE_DESIGN.md Section 2) and is reported here again, at
   build time, as an observed fact — not silently reconciled or forced
   to match by altering the transform logic.

2. Drone vs. Airplane average fused-track duration: NOT ANSWERABLE from
   this data as currently classified. proto.tower.TrackObjectClass (the
   enum backing fused_track_states.object_class_raw/_name) has no DRONE
   or AIRPLANE value at all (docs/architecture/DATABASE_DESIGN.md Section 3) — this
   was independently re-confirmed via direct protobuf enum reflection
   during Stage 4/5A, not assumed. The pipeline does not fabricate a
   Drone/Airplane mapping to force an answer; v_fused_track_summary
   (sql/views.sql) provides per-track duration, but resolving "the"
   object class per track (5 possible semantics identified, none
   selected — docs/architecture/SCHEMA_REVIEW.md finding F6) remains an explicit,
   human-decided step outside this pipeline's scope.

3. Timestamp unit bug found and fixed during Stage 6 validation (not a
   schema issue): fused_track_states.create_timestamp_ns,
   last_measurement_timestamp_ns, and fused_track_measurements.
   measurement_timestamp_ns were initially loaded assuming the source
   protobuf fields were already nanoseconds. check_timestamp_magnitude
   flagged them as ~1000x too small versus each message's own confirmed-
   nanosecond log_time_ns. Direct measurement (ratio of each field
   against log_time_ns) gave exactly 1000.0000000... across every
   sample, proving the source fields are microseconds. Fixed in
   src/cuas_etl/transform.py (MICROSECONDS_TO_NANOSECONDS conversion,
   applied at all 3 call sites) — a transform-layer correction; the
   destination SQLite column types were already correct. Reported to
   the user at the time it was found, per the progress-reporting
   requirement.

4 orphaned detection<->track pairings (last_associated_detection_id
values with no matching cv_detections row) were excluded from
cv_detection_track_links and logged in data_quality_issues instead of
being silently dropped or breaking referential integrity — this count
matches the 4 CONFIRMED in Stage 3/4.

DETERMINISM
-----------
tests/test_etl_integration.py proves two independent, from-scratch
rebuilds of the database produce identical results for: every row in
every table (surrogate ids, all field values), the deduplicated
cv_detection_track_links bridge pairs, the data_quality_issues records
(excluding detected_at_utc, which is a build-wall-clock timestamp by

random UUIDs are used anywhere; every surrogate id is assigned by a
documented, fixed traversal order over the source file.

ERROR-HANDLING POLICY (as required)
------------------------------------
src/cuas_etl/load.py contains no blanket INSERT OR IGNORE and no
blanket "except sqlite3.IntegrityError: continue" anywhere. The single
recoverable case (the 4 orphaned bridge pairs) is handled by excluding
those rows in transform.py before they ever reach load.py — they are
never presented to SQLite as an insert attempt. Every other constraint
violation is fatal: the responsible SAVEPOINT is rolled back, the
table/source_message_id/field/row values are reported via LoadError,
and the process exits nonzero. A non-rebuild run against an
already-populated database validates and exits cleanly without
reloading (see database_already_populated() in load.py).

STAGE 6B ADDENDUM — Checksum resolution follow-up
=======================================================================

SCOPE
-----
Following Stage 6, both of CLAUDE.md's expected analytical checksums
(~81% CV incorporation; ~30s Drone / ~600s Airplane average fused-track
duration) were investigated across several rounds, consolidated into
the single canonical docs/analytics/CHECKSUM_RESOLUTION.md (Stage 9 documentation
cleanup merged two superseded interim investigation documents into it),
plus this Stage 6B follow-up. This addendum records the two outcomes
and the small, evidence-supported change implemented as a result. No
schema table, no ETL transformation, and no bridge-table logic was
changed for either checksum.

DRONE/AIRPLANE — RESOLVED
--------------------------
Root cause: proto.tower.TrackObjectClass (the enum backing
fused_track_states.object_class_raw/_name) has no DRONE or AIRPLANE
value at all, confirmed by full protobuf descriptor enumeration. The
classification is instead carried by measurement provenance — which
sensor contributed to a track — a field (proto.tower.SensorId, raw
value 6 = TOWER_SENSOR_TRANSPONDER) already extracted and loaded,
unchanged, as fused_track_measurements.sensor_id_raw/_name.

Implemented: one new view, v_fused_track_type_basis (sql/views.sql),
and one new query, queries/fused_track_duration_by_type.sql. No new
column, no new table, no ETL mapping change.

Classification:
  Airplane := ever has a TOWER_SENSOR_TRANSPONDER measurement
  Drone    := never does, AND dominant object_class is
              OBJECT_CLASS_AIR_VEHICLE or OBJECT_CLASS_UNKNOWN_AIR_VEHICLE
              (excludes OBJECT_CLASS_BIRD-dominant tracks)

Observed results (arithmetic mean, the statistic the assignment asks
for — median reported only as supplementary information, never
substituted):
  Airplane: n=36, mean 614.68s (target ~600s, +2.4%)
  Drone:    n=51, mean 35.86s  (target ~30s,  +19.5% — reported
            honestly; the median, 30.26s, is much closer but is not
            claimed as "the" answer)

CV INCORPORATION — CLARIFICATION REQUIRED
-------------------------------------------
A final semantic search (assignment text, README.md, CLAUDE.md,
embedded protobuf SourceCodeInfo comments across all 4 schemas'
FileDescriptorSets, custom/extension field options, MCAP metadata
records, MCAP attachments) found no explicit source definition of
"incorporated" beyond what the existing cv_detection_track_links
derivation already implements. Status-code event counting,
counter-delta semantics (computed correctly, not summed naively),
denominator-eligibility fields, frame-level grain, track-birth events,
and time-alignment matching were all re-tested from raw MCAP data and
converge on the same 97.54% figure (or 99.95% for the one
cumulative-sum method explicitly excluded as incorrect). No natural,
source-supported population of the ~1,538-1,557 size implied by ~81%
was found. No production change was made. A clarification question for
Anduril is prepared in docs/analytics/CHECKSUM_RESOLUTION.md.
